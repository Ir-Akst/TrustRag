## 1. Phase 2 Enhancements and Hardening

While Phase 2 previously applied a slice `[:_MAX_B64_CANDIDATES]`, it suffered from two secondary resource inefficiencies:
1. **Eager List Materialization:** `_BASE64_CANDIDATE_RE.findall(text)` constructed a full list of all matching candidates across the document before slicing `[:64]`. Under a 10,000-candidate attack, this allocated an unnecessary array of 10,000 string pointers.
2. **Unbounded Sub-Candidate Splitting:** In `_split_adjacent_candidates(raw)`, if an adversary crafted a single candidate token of 8,000 characters packed with hundreds of slash-separated sub-tokens (`/{A}/{B}/{C}...`), the function would expand into more than 64 subcandidates.

### Refactored Implementation

1. **Lazy Streaming in Phase 2:**
   ```python
   phase2_count = 0
   for match_obj in _BASE64_CANDIDATE_RE.finditer(text):
       if phase2_count >= _MAX_B64_CANDIDATES:
           break
       raw = match_obj.group(0)
       phase2_count += 1
       if len(raw) > _MAX_B64_TOKEN_LEN:
           continue
   ```

2. **Sub-Candidate Bounding in `_split_adjacent_candidates()`:**
   ```python
   if len(subcandidates) >= _MAX_B64_CANDIDATES:
       break
   ```
   Enforced across all three splitting phases: delimiter runs (`//+`, `+++`), intermediate equals padding (`=+`), and single-slash splits.
